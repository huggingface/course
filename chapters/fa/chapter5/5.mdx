گاهی دیتاستی که برای ساخت یک برنامه‌ی NLP به آن نیاز دارید وجود ندارد، بنابراین باید خودتان آن را بسازید. در این بخش نشان می‌دهیم چگونه پیکره‌ای از [issueهای GitHub](https://github.com/features/issues/) بسازید؛ issueهایی که معمولاً برای پیگیری باگ‌ها یا قابلیت‌ها در مخزن‌های GitHub استفاده می‌شوند. این پیکره را می‌توان برای اهداف مختلفی به کار برد، از جمله:

<div dir="rtl">

* بررسی مدت‌زمان بسته شدن issueها یا pull requestهای باز
* تعلیم یک _دسته‌بند چندبرچسبی_ که بتواند بر اساس توضیح issue، متادیتاهایی مانند «باگ»، «بهبود» یا «پرسش» را به آن برچسب بزند
* ساختن موتور جست‌وجوی معنایی برای پیدا کردن issueهایی که با پرس‌وجوی کاربر مطابقت دارند

</div>

در اینجا روی ساخت پیکره تمرکز می‌کنیم و در بخش بعدی سراغ برنامه‌ی جست‌وجوی معنایی می‌رویم. برای اینکه بحث همچنان رنگ‌وبوی متادیتا داشته باشد، از issueهای GitHub مربوط به یک پروژه‌ی متن‌باز محبوب، یعنی 🤗 Datasets، استفاده می‌کنیم! بیایید ببینیم چگونه داده‌ها را به دست آوریم و اطلاعات موجود در این issueها را بررسی کنیم.

برای دانلود همه‌ی issueهای مخزن، از [GitHub REST API](https://docs.github.com/en/rest) برای فراخوانی endpoint [`Issues`](https://docs.github.com/en/rest/reference/issues#list-repository-issues) استفاده می‌کنیم. این endpoint فهرستی از اشیای JSON برمی‌گرداند که هرکدام تعداد زیادی فیلد، از جمله عنوان و توضیح و متادیتایی درباره‌ی وضعیت issue و موارد دیگر، دارند.

یک راه مناسب برای دانلود issueها استفاده از کتابخانه‌ی `requests` است که روش استاندارد ارسال درخواست‌های HTTP در پایتون به شمار می‌رود. می‌توانید این کتابخانه را با اجرای دستور زیر نصب کنید:

> [!TIP]
> ✏️ **امتحان کنید!** روی چند URL موجود در payload JSON بالا کلیک کنید تا ببینید هر issue به چه نوع اطلاعاتی مرتبط است.

طبق توضیح [مستندات GitHub](https://docs.github.com/en/rest/overview/resources-in-the-rest-api#rate-limiting)، درخواست‌های بدون احراز هویت به ۶۰ درخواست در ساعت محدود هستند. اگرچه می‌توانید پارامتر `per_page` را افزایش دهید تا تعداد درخواست‌ها کم شود، روی هر مخزنی که بیش از چند هزار issue داشته باشد باز هم به محدودیت نرخ درخواست می‌خورید. بنابراین باید [دستورالعمل GitHub](https://docs.github.com/en/github/authenticating-to-github/creating-a-personal-access-token) برای ساخت یک _personal access token_ را دنبال کنید تا محدودیت نرخ را به ۵۰۰۰ درخواست در ساعت افزایش دهید. پس از ساخت توکِن، می‌توانید آن را در بخشی از header درخواست قرار دهید:

<div dir="ltr">

```py
GITHUB_TOKEN = xxx  # Copy your GitHub token here
headers = {"Authorization": f"token {GITHUB_TOKEN}"}
```

</div>

> [!WARNING]
> ⚠️ نوت‌بوکی را که `GITHUB_TOKEN` در آن وارد شده است به اشتراک نگذارید. پیشنهاد می‌کنیم پس از اجرای آخرین سلول، آن را حذف کنید تا این اطلاعات تصادفاً افشا نشود. حتی بهتر است توکِن را در یک فایل *.env* ذخیره کنید و از [`python-dotenv`](https://github.com/theskumar/python-dotenv) برای بارگذاری خودکار آن به‌عنوان متغیر محیطی استفاده کنید.

حالا که توکِن دسترسی خود را داریم، تابعی می‌سازیم که بتواند همه‌ی issueهای یک مخزن GitHub را دانلود کند:

<div dir="ltr">

```py
import time
import math
from pathlib import Path
import pandas as pd
from tqdm.notebook import tqdm


def fetch_issues(
    owner="huggingface",
    repo="datasets",
    num_issues=10_000,
    rate_limit=5_000,
    issues_path=Path("."),
):
    if not issues_path.is_dir():
        issues_path.mkdir(exist_ok=True)

    batch = []
    all_issues = []
    per_page = 100  # Number of issues to return per page
    num_pages = math.ceil(num_issues / per_page)
    base_url = "https://api.github.com/repos"

    for page in tqdm(range(num_pages)):
        # Query with state=all to get both open and closed issues
        query = f"issues?page={page}&per_page={per_page}&state=all"
        issues = requests.get(f"{base_url}/{owner}/{repo}/{query}", headers=headers)
        batch.extend(issues.json())

        if len(batch) > rate_limit and len(all_issues) < num_issues:
            all_issues.extend(batch)
            batch = []  # Flush batch for next time period
            print(f"Reached GitHub rate limit. Sleeping for one hour ...")
            time.sleep(60 * 60 + 1)

    all_issues.extend(batch)
    df = pd.DataFrame.from_records(all_issues)
    df.to_json(f"{issues_path}/{repo}-issues.jsonl", orient="records", lines=True)
    print(
        f"Downloaded all the issues for {repo}! Dataset stored at {issues_path}/{repo}-issues.jsonl"
    )
```

</div>

عالی است، نخستین دیتاست خود را از صفر ساختیم! اما چرا چند هزار issue وجود دارد، در حالی که [زبانه‌ی Issues](https://github.com/huggingface/datasets/issues) مخزن 🤗 Datasets در مجموع فقط حدود ۱۰۰۰ issue نشان می‌دهد 🤔؟ همان‌طور که در [مستندات GitHub](https://docs.github.com/en/rest/reference/issues#list-issues-assigned-to-the-authenticated-user) توضیح داده شده است، دلیلش این است که همه‌ی pull requestها را نیز دانلود کرده‌ایم:

> از دید GitHub REST API v3، هر pull request یک issue محسوب می‌شود، اما هر issue یک pull request نیست. به همین دلیل endpointهای «Issues» ممکن است هم issueها و هم pull requestها را در پاسخ برگردانند. می‌توانید pull requestها را با کلید `pull_request` شناسایی کنید. توجه داشته باشید `id` یک pull request که از endpointهای «Issues» برگردانده می‌شود، شناسه‌ی یک issue خواهد بود.

از آنجا که محتوای issueها و pull requestها کاملاً متفاوت است، بیایید پیش‌پردازش کوچکی انجام دهیم تا بتوانیم آن‌ها را از هم تشخیص دهیم.

## پاک‌سازی داده‌ها[[cleaning-up-the-data]]

قطعه‌ی بالا از مستندات GitHub به ما می‌گوید که می‌توان از ستون `pull_request` برای تشخیص issueها از pull requestها استفاده کرد. بیایید یک نمونه‌ی تصادفی ببینیم تا تفاوت آن‌ها مشخص شود. همان‌طور که در [بخش ۳](/course/chapter5/3) انجام دادیم، توابع `Dataset.shuffle()` و `Dataset.select()` را زنجیره می‌کنیم تا یک نمونه‌ی تصادفی بسازیم، سپس ستون‌های `html_url` و `pull_request` را با هم zip می‌کنیم تا URLهای مختلف را مقایسه کنیم:

<div dir="ltr">

```py
sample = issues_dataset.shuffle(seed=666).select(range(3))

# Print out the URL and pull request entries
for url, pr in zip(sample["html_url"], sample["pull_request"]):
    print(f">> URL: {url}")
    print(f">> Pull request: {pr}\n")
```

در اینجا می‌بینیم هر pull request با چند URL مرتبط است، در حالی که issueهای معمولی ورودی `None` دارند. می‌توانیم از این تفاوت استفاده کنیم و ستون جدیدی به نام `is_pull_request` بسازیم که بررسی کند فیلد `pull_request` مقدار `None` دارد یا نه:

<div dir="ltr">

```py
issues_dataset = issues_dataset.map(
    lambda x: {"is_pull_request": False if x["pull_request"] is None else True}
)
```

> [!TIP]
> ✏️ **امتحان کنید!** میانگین زمان بسته شدن issueها در 🤗 Datasets را محاسبه کنید. احتمالاً تابع `Dataset.filter()` برای فیلتر کردن pull requestها و issueهای باز مفید خواهد بود و می‌توانید از تابع `Dataset.set_format()` برای تبدیل دیتاست به `DataFrame` استفاده کنید تا دست‌کاری timestampهای `created_at` و `closed_at` آسان‌تر شود. برای امتیاز بیشتر، میانگین زمان بسته شدن pull requestها را نیز محاسبه کنید.

اگرچه می‌توانستیم با حذف یا تغییر نام برخی ستون‌ها دیتاست را بیشتر پاک‌سازی کنیم، در این مرحله معمولاً بهتر است دیتاست را تا حد امکان «خام» نگه داریم تا بتوان به‌سادگی از آن در برنامه‌های مختلف استفاده کرد.

پیش از push کردن دیتاست به هاب هاگینگ‌فِیس، بیایید با چیزی که در آن کم است برخورد کنیم: commentهای مربوط به هر issue و pull request. در ادامه آن‌ها را اضافه می‌کنیم — بله، درست حدس زدید — با GitHub REST API!

## بارگذاری دیتاست در هاب هاگینگ‌فِیس[[uploading-the-dataset-to-the-hugging-face-hub]]

<Youtube id="HaN6qCr_Afc"/>

حالا که دیتاست غنی‌شده‌ی خود را داریم، وقت آن است که آن را به هاب push کنیم تا بتوانیم با جامعه کاربران به اشتراک بگذاریم! بارگذاری دیتاست بسیار ساده است: درست مانند مدل‌ها و توکِنایزرهای 🤗 Transformers، می‌توانیم از متد `push_to_hub()` برای push کردن دیتاست استفاده کنیم. برای این کار به توکِن احراز هویتی نیاز داریم که با ورود به هاب هاگینگ‌فِیس و استفاده از تابع `notebook_login()` به دست می‌آید:

<div dir="ltr">

```py
from huggingface_hub import notebook_login

notebook_login()
```

</div>

این کار widgetی ایجاد می‌کند که می‌توانید نام کاربری و گذرواژه‌ی خود را در آن وارد کنید و توکِن API در *~/.huggingface/token* ذخیره می‌شود. اگر کد را در ترمینال اجرا می‌کنید، می‌توانید به‌جای آن با CLI وارد شوید:

<div dir="ltr">

```bash
huggingface-cli login
```

</div>

پس از انجام این کار، می‌توانیم با اجرای دستور زیر دیتاست را بارگذاری کنیم:

<div dir="ltr">

```py
issues_with_comments_dataset.push_to_hub("github-issues")
```

</div>

از اینجا به بعد، هرکس می‌تواند با دادن شناسه‌ی مخزن به آرگومان `path` تابع `load_dataset()` دیتاست را دانلود کند:

## ساختن کارت دیتاست[[creating-a-dataset-card]]

دیتاست‌هایی که خوب مستند شده‌اند احتمال بیشتری دارد برای دیگران (از جمله خود آینده‌ی شما!) مفید باشند، چون زمینه‌ای فراهم می‌کنند تا کاربران تصمیم بگیرند دیتاست برای مسئله‌ی آن‌ها مناسب است یا نه و سوگیری‌ها یا خطرهای احتمالی استفاده از دیتاست را ارزیابی کنند.

در هاب هاگینگ‌فِیس، این اطلاعات در فایل *README.md* هر مخزن دیتاست ذخیره می‌شود. پیش از ساختن این فایل، دو گام اصلی وجود دارد:

<div dir="rtl">

1. از برنامه‌ی [`datasets-tagging`](https://huggingface.co/datasets/tagging/) برای ساخت برچسب‌های متادیتا در قالب YAML استفاده کنید. این برچسب‌ها برای قابلیت‌های مختلف جست‌وجو در هاب هاگینگ‌فِیس به کار می‌روند و باعث می‌شوند اعضای جامعه بتوانند به‌راحتی دیتاست شما را پیدا کنند. چون در اینجا دیتاستی سفارشی ساخته‌ایم، باید مخزن `datasets-tagging` را clone کنید و برنامه را به‌صورت محلی اجرا کنید. رابط برنامه به شکل زیر است:

</div>

<div class="flex justify-center">
<img src="https://huggingface.co/datasets/huggingface-course/documentation-images/resolve/main/en/chapter5/datasets-tagger.png" alt="رابط `datasets-tagging`." width="80%"/>
</div>

<div dir="rtl">

2. [راهنمای 🤗 Datasets](https://github.com/huggingface/datasets/blob/master/templates/README_guide.md) درباره‌ی ساخت کارت‌های دیتاست آموزنده را بخوانید و از آن به‌عنوان الگو استفاده کنید.

</div>

می‌توانید فایل *README.md* را مستقیماً در هاب بسازید و یک کارت دیتاست نمونه را در مخزن دیتاست `lewtun/github-issues` پیدا کنید. تصویر زیر نمونه‌ای از کارت دیتاست تکمیل‌شده را نشان می‌دهد.

<div class="flex justify-center">
<img src="https://huggingface.co/datasets/huggingface-course/documentation-images/resolve/main/en/chapter5/dataset-card.png" alt="یک کارت دیتاست." width="80%"/>
</div>

> [!TIP]
> ✏️ **امتحان کنید!** از برنامه‌ی `dataset-tagging` و [راهنمای 🤗 Datasets](https://github.com/huggingface/datasets/blob/master/templates/README_guide.md) استفاده کنید تا فایل *README.md* دیتاست issueهای GitHub خود را تکمیل کنید.

همین بود! در این بخش دیدیم که ساختن یک دیتاست خوب می‌تواند کار نسبتاً پیچیده‌ای باشد، اما خوشبختانه بارگذاری و به‌اشتراک‌گذاری آن با جامعه پیچیده نیست. در بخش بعدی از دیتاست جدیدمان برای ساختن یک موتور جست‌وجوی معنایی با 🤗 Datasets استفاده می‌کنیم که می‌تواند پرسش‌ها را با مرتبط‌ترین issueها و commentها تطبیق دهد.

> [!TIP]
> ✏️ **امتحان کنید!** مراحلی را که در این بخش برای ساخت دیتاستی از issueهای GitHub طی کردیم، برای کتابخانه‌ی متن‌باز موردعلاقه‌ی خود تکرار کنید (البته پروژه‌ای غیر از 🤗 Datasets انتخاب کنید!). برای امتیاز بیشتر، یک دسته‌بند چندبرچسبی را کوک کنید تا برچسب‌های موجود در فیلد `labels` را پیش‌بینی کند.

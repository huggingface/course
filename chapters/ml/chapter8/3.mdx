ഇടതുവശത്ത്, വിവിധ ടോപ്പിക്കുകൾ (topics) തരംതിരിച്ചിരിക്കുന്ന എല്ലാ കാറ്റഗറികളും നിങ്ങൾക്ക് കാണാം; വലതുവശത്ത് ഏറ്റവും പുതിയ ടോപ്പിക്കുകൾ കാണിക്കുന്നു. ഒരു തലക്കെട്ടും കാറ്റഗറിയും വിവരണവും അടങ്ങിയ ഒരു പോസ്‌റ്റാണ് ടോപ്പിക്ക്; [അധ്യായം 5](/course/chapter5)-ൽ നമ്മുടെ സ്വന്തം ഡേറ്റാസെറ്റ് ഉണ്ടാക്കുമ്പോൾ കണ്ട GitHub ഇഷ്യൂ ഫോർമാറ്റിനോട് ഇത് ഏറെ സാമ്യമുള്ളതാണ്. പേര് സൂചിപ്പിക്കുന്നതുപോലെ, [Beginners](https://discuss.huggingface.co/c/beginners/5) കാറ്റഗറി പ്രധാനമായും Hugging Face ലൈബ്രറികളും ഇക്കോസിസ്‌റ്റവും ഉപയോഗിച്ച് തുടങ്ങുന്നവർക്കായുള്ളതാണ്. ഏതെങ്കിലും ലൈബ്രറിയെക്കുറിച്ചുള്ള ഏത് ചോദ്യവും അവിടെ സ്വാഗതം ചെയ്യുന്നു — കുറച്ച് കോഡ് ഡീബഗ് ചെയ്യാനായാലും, എന്തെങ്കിലും എങ്ങനെ ചെയ്യണം എന്നതിനെക്കുറിച്ച് സഹായം ചോദിക്കാനായാലും. (എന്നിരുന്നാലും, നിങ്ങളുടെ ചോദ്യം ഒരു പ്രത്യേക ലൈബ്രറിയെക്കുറിച്ചാണെങ്കിൽ, ഫോറത്തിലെ ആ ലൈബ്രറിയുടെ കാറ്റഗറിയിലേക്ക് പോകുന്നതാവും നല്ലത്.)

അതുപോലെ, [Intermediate](https://discuss.huggingface.co/c/intermediate/6), [Research](https://discuss.huggingface.co/c/research/7) കാറ്റഗറികൾ കൂടുതൽ വിപുലമായ ചോദ്യങ്ങൾക്കുള്ളതാണ് — ഉദാഹരണത്തിന്, ലൈബ്രറികളെക്കുറിച്ചോ, ചർച്ച ചെയ്യാൻ ആഗ്രഹിക്കുന്ന രസകരമായ ഏതെങ്കിലും പുതിയ NLP ഗവേഷണത്തെക്കുറിച്ചോ.

സ്വാഭാവികമായും, [Course](https://discuss.huggingface.co/c/course/20) കാറ്റഗറിയെക്കുറിച്ചും പറയേണ്ടതുണ്ട്; Hugging Face കോഴ്‌സുമായി ബന്ധപ്പെട്ട ഏത് ചോദ്യവും അവിടെ നിങ്ങൾക്ക് ചോദിക്കാം!

ഒരു കാറ്റഗറി തിരഞ്ഞെടുത്തുകഴിഞ്ഞാൽ, നിങ്ങളുടെ ആദ്യ ടോപ്പിക്ക് എഴുതാൻ നിങ്ങൾ തയ്യാറായി. ഇത് എങ്ങനെ ചെയ്യണം എന്നതിനെക്കുറിച്ചുള്ള ചില [മാർഗ്ഗനിർദ്ദേശങ്ങൾ](https://discuss.huggingface.co/t/how-to-request-support/3128) ഫോറത്തിൽ കാണാം; ഒരു നല്ല ടോപ്പിക്കിന്റെ സവിശേഷതകൾ ഈ ഭാഗത്തിൽ നമ്മൾ പരിശോധിക്കും.

## ഒരു നല്ല ഫോറം പോസ്‌റ്റ് എഴുതുന്നു[[writing-a-good-forum-post]]

തുടർച്ചയായ ഉദാഹരണമായി, ഒരു കസ്‌റ്റം സെർച്ച് എഞ്ചിൻ ഉണ്ടാക്കാൻ Wikipedia ലേഖനങ്ങളിൽ നിന്ന് എംബെഡ്ഡിംഗുകൾ ഉണ്ടാക്കാൻ നമ്മൾ ശ്രമിക്കുന്നു എന്ന് കരുതുക. പതിവുപോലെ, ടോക്കണൈസറും മോഡലും ഇങ്ങനെ ലോഡ് ചെയ്യുന്നു:

```python
from transformers import AutoTokenizer, AutoModel

model_checkpoint = "distilbert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_checkpoint)
model = AutoModel.from_pretrained(model_checkpoint)
```

നമുക്ക് സഹായം വേണ്ട എറർ സന്ദേശം ഈ ടോപ്പിക്കിൽ ഉണ്ടെങ്കിലും, അത് എഴുതിയിരിക്കുന്ന രീതിയിൽ ചില പ്രശ്നങ്ങളുണ്ട്:

1. തലക്കെട്ട് അത്ര വിവരണാത്മകമല്ല; അതിനാൽ ഫോറം നോക്കുന്ന ഒരാൾക്ക്, ഉള്ളടക്കം കൂടി വായിക്കാതെ ടോപ്പിക്ക് എന്തിനെക്കുറിച്ചാണെന്ന് പറയാൻ കഴിയില്ല.
2. എറർ _എവിടെ നിന്ന്_ വരുന്നു, അത് _എങ്ങനെ_ പുനഃസൃഷ്ടിക്കാം (reproduce) എന്നിവയെക്കുറിച്ച് ഉള്ളടക്കം മതിയായ വിവരങ്ങൾ നൽകുന്നില്ല.
3. ടോപ്പിക്ക് ഏതാനും ആളുകളെ നേരിട്ട് ടാഗ് ചെയ്യുന്നു, അതും കുറച്ച് ആജ്ഞാപിക്കുന്ന സ്വരത്തിൽ.

ഇതുപോലുള്ള ടോപ്പിക്കുകൾക്ക് വേഗത്തിൽ ഉത്തരം കിട്ടാൻ സാധ്യത കുറവാണ് (ഉത്തരം കിട്ടിയാൽ തന്നെ); അതിനാൽ ഇത് എങ്ങനെ മെച്ചപ്പെടുത്താം എന്ന് നോക്കാം. ഒരു നല്ല തലക്കെട്ട് തിരഞ്ഞെടുക്കുക എന്ന ആദ്യ പ്രശ്നത്തിൽ നിന്ന് തുടങ്ങാം.

### വിവരണാത്മകമായ ഒരു തലക്കെട്ട് തിരഞ്ഞെടുക്കുന്നു[[choosing-a-descriptive-title]]

നിങ്ങളുടെ കോഡിലെ ഒരു ബഗിന് സഹായം തേടുകയാണെങ്കിൽ, നിങ്ങളുടെ ചോദ്യത്തിന് ഉത്തരം നൽകാൻ കഴിയുമോ ഇല്ലയോ എന്ന് മറ്റുള്ളവർക്ക് വേഗത്തിൽ തീരുമാനിക്കാൻ കഴിയുന്ന വിധത്തിൽ മതിയായ വിവരങ്ങൾ തലക്കെട്ടിൽ ഉൾപ്പെടുത്തുക എന്നതാണ് ഒരു നല്ല പൊതുതത്വം. നമ്മുടെ ഉദാഹരണത്തിൽ, ഉയർത്തപ്പെടുന്ന എക്‌സെപ്‌ഷന്റെ പേര് നമുക്കറിയാം; `model(**inputs)` വിളിക്കുന്ന മോഡലിന്റെ ഫോർവേഡ് പാസ്സിലാണ് അത് ഉണ്ടാകുന്നത് എന്നതിന് ചില സൂചനകളുമുണ്ട്. ഇത് അറിയിക്കാൻ, ഇങ്ങനെയൊരു തലക്കെട്ട് ആകാം:

> Source of IndexError in the AutoModel forward pass?

ബഗ് _എവിടെ നിന്ന്_ വരുന്നു എന്ന് നിങ്ങൾ കരുതുന്നു എന്നത് ഈ തലക്കെട്ട് വായനക്കാരനോട് പറയുന്നു; മുമ്പ് ഒരു `IndexError` നേരിട്ടിട്ടുള്ളവരാണെങ്കിൽ, അത് എങ്ങനെ ഡീബഗ് ചെയ്യണം എന്ന് അവർക്ക് അറിയാൻ നല്ല സാധ്യതയുണ്ട്. തീർച്ചയായും, തലക്കെട്ട് നിങ്ങൾക്ക് ഇഷ്ടമുള്ളതെന്തും ആകാം; ഇതുപോലുള്ള മറ്റ് രൂപങ്ങളും:

> Why does my model produce an IndexError?

നന്നായിരിക്കും. വിവരണാത്മകമായ ഒരു തലക്കെട്ട് ഇപ്പോൾ നമുക്കുണ്ട്; ഇനി ഉള്ളടക്കം മെച്ചപ്പെടുത്തുന്നത് നോക്കാം.

### നിങ്ങളുടെ കോഡ് സ്‌നിപ്പെറ്റുകൾ ഫോർമാറ്റ് ചെയ്യുന്നു[[formatting-your-code-snippets]]

ഒരു IDE-യിൽ തന്നെ സോഴ്‌സ് കോഡ് വായിക്കുന്നത് ബുദ്ധിമുട്ടാണ്; കോഡ് പ്ലെയിൻ ടെക്‌സ്‌റ്റായി കോപ്പി-പേസ്‌റ്റ് ചെയ്യുമ്പോൾ അത് അതിലും ബുദ്ധിമുട്ടാകും! ഭാഗ്യവശാൽ, Hugging Face ഫോറങ്ങൾ Markdown സപ്പോർട്ട് ചെയ്യുന്നു; അതിനാൽ കൂടുതൽ എളുപ്പത്തിൽ വായിക്കാവുന്നതിനായി നിങ്ങളുടെ കോഡ് ബ്ലോക്കുകൾ എപ്പോഴും മൂന്ന് ബാക്ക്‌ടിക്കുകൾക്കുള്ളിൽ (```) വയ്ക്കണം. എറർ സന്ദേശം ഭംഗിയാക്കാൻ ഇത് ചെയ്യാം -- അതോടൊപ്പം, നമ്മുടെ ആദ്യ പതിപ്പിനെക്കാൾ ഉള്ളടക്കം കുറച്ചുകൂടി മര്യാദയുള്ളതാക്കുകയും ചെയ്യാം:

സ്‌ക്രീൻഷോട്ടിൽ കാണുന്നതുപോലെ, കോഡ് ബ്ലോക്കുകൾ ബാക്ക്‌ടിക്കുകൾക്കുള്ളിൽ വയ്ക്കുന്നത് അസംസ്‌കൃത ടെക്‌സ്‌റ്റിനെ, കളർ സ്‌റ്റൈലിംഗ് സഹിതം, ഫോർമാറ്റ് ചെയ്ത കോഡാക്കി മാറ്റുന്നു! `distilbert-base-uncased`-ന് നമ്മൾ ചെയ്തതുപോലെ, ഇൻലൈൻ വേരിയബിളുകൾ ഫോർമാറ്റ് ചെയ്യാൻ ഒറ്റ ബാക്ക്‌ടിക്കുകൾ ഉപയോഗിക്കാം എന്നതും ശ്രദ്ധിക്കുക. ഈ ടോപ്പിക്ക് ഇപ്പോൾ വളരെ മെച്ചപ്പെട്ടതായി തോന്നുന്നു; കുറച്ച് ഭാഗ്യമുണ്ടെങ്കിൽ, എറർ എന്തിനെക്കുറിച്ചാണെന്ന് ഊഹിക്കാൻ കഴിയുന്ന ഒരാളെ കമ്മ്യൂണിറ്റിയിൽ നമുക്ക് കണ്ടെത്താനാവും. എന്നാൽ, ഭാഗ്യത്തെ ആശ്രയിക്കുന്നതിനു പകരം, traceback അതിന്റെ മുഴുവൻ വിശദാംശങ്ങളോടെയും ഉൾപ്പെടുത്തി കാര്യങ്ങൾ എളുപ്പമാക്കാം!

### മുഴുവൻ traceback-ഉം ഉൾപ്പെടുത്തുന്നു[[including-the-full-traceback]]

സ്വന്തം കോഡ് ഡീബഗ് ചെയ്യാൻ traceback-ന്റെ അവസാന വരി മാത്രം മതിയാകുന്നതിനാൽ, "സ്ഥലം ലാഭിക്കാൻ" ടോപ്പിക്കിൽ അതു മാത്രം നൽകാൻ തോന്നാം. ഉദ്ദേശ്യം നല്ലതാണെങ്കിലും, ഇത് യഥാർത്ഥത്തിൽ മറ്റുള്ളവർക്ക് പ്രശ്നം ഡീബഗ് ചെയ്യുന്നത് _കൂടുതൽ ബുദ്ധിമുട്ടാക്കുന്നു_; കാരണം traceback-ന്റെ മുകൾ ഭാഗത്തുള്ള വിവരങ്ങളും ശരിക്കും ഉപകാരപ്രദമാകും. അതിനാൽ, _മുഴുവൻ_ traceback-ഉം കോപ്പി-പേസ്‌റ്റ് ചെയ്യുകയും, അത് ഭംഗിയായി ഫോർമാറ്റ് ചെയ്തിട്ടുണ്ടെന്ന് ഉറപ്പുവരുത്തുകയും ചെയ്യുന്നതാണ് നല്ല രീതി. ഈ traceback-കൾ കുറച്ച് നീണ്ടതാകാമെന്നതിനാൽ, സോഴ്‌സ് കോഡ് വിശദീകരിച്ചതിനു ശേഷം അവ കാണിക്കാനാണ് ചിലർ ഇഷ്ടപ്പെടുന്നത്. നമുക്കും അങ്ങനെ ചെയ്യാം. ഇപ്പോൾ, നമ്മുടെ ഫോറം ടോപ്പിക്ക് ഇങ്ങനെയാണ്:

> Token indices sequence length is longer than the specified maximum sequence length for this model (583 > 512).

എന്നിരുന്നാലും, എറർ ഉണ്ടാക്കിയ യഥാർത്ഥ കോഡ് നൽകി അവർക്ക് കാര്യങ്ങൾ കൂടുതൽ എളുപ്പമാക്കാം. ഇപ്പോൾ അത് ചെയ്യാം.

### പുനഃസൃഷ്ടിക്കാവുന്ന ഒരു ഉദാഹരണം നൽകുന്നു[[providing-a-reproducible-example]]

മറ്റൊരാളുടെ കോഡ് ഡീബഗ് ചെയ്യാൻ നിങ്ങൾ എപ്പോഴെങ്കിലും ശ്രമിച്ചിട്ടുണ്ടെങ്കിൽ, അവർ റിപ്പോർട്ട് ചെയ്ത പ്രശ്നം ആദ്യം പുനഃസൃഷ്ടിക്കാനായിരിക്കും നിങ്ങൾ ശ്രമിച്ചിട്ടുണ്ടാവുക; അങ്ങനെ traceback-ലൂടെ കടന്നുപോയി എറർ കൃത്യമായി കണ്ടെത്താൻ തുടങ്ങാം. ഫോറങ്ങളിൽ സഹായം നേടുന്ന (അല്ലെങ്കിൽ നൽകുന്ന) കാര്യത്തിലും ഇത് വ്യത്യസ്തമല്ല; അതിനാൽ എറർ പുനഃസൃഷ്ടിക്കുന്ന ഒരു ചെറിയ ഉദാഹരണം നൽകാൻ കഴിഞ്ഞാൽ അത് ശരിക്കും സഹായകമാകും. പലപ്പോഴും, ഈ വ്യായാമത്തിലൂടെ കടന്നുപോകുന്നതു തന്നെ എന്താണ് പിഴയ്ക്കുന്നത് എന്ന് കണ്ടെത്താൻ നിങ്ങളെ സഹായിക്കും. എന്തായാലും, നമ്മുടെ ഉദാഹരണത്തിൽ കുറവുള്ള ഭാഗം, മോഡലിന് നമ്മൾ നൽകിയ _ഇൻപുട്ടുകൾ_ കാണിക്കുക എന്നതാണ്. അത് ചെയ്താൽ, താഴെ കാണുന്നതുപോലെ പൂർത്തിയാക്കിയ ഒരു ഉദാഹരണം കിട്ടും:

## ട്രെയിനിംഗ് പൈപ്പ്‌ലൈൻ ഡീബഗ് ചെയ്യുന്നു[[debugging-the-training-pipeline]]

<Youtube id="N9kO52itd0Q"/>

`model.fit()`-ൽ ഒരു എറർ നേരിടുമ്പോഴുള്ള പ്രശ്നം, ആ ഘട്ടം വരെ നിങ്ങൾ ചെയ്തുകൊണ്ടിരുന്ന ഒരുപാട് കാര്യങ്ങൾ ട്രെയിനിംഗ് ഒരുമിച്ചു ചേർക്കുന്നതിനാൽ, അത് പല ഉറവിടങ്ങളിൽ നിന്നും വരാം എന്നതാണ്. പ്രശ്നം നിങ്ങളുടെ ഡേറ്റാസെറ്റിലെ എന്തെങ്കിലും തകരാറോ, ഡേറ്റാസെറ്റിലെ ഘടകങ്ങൾ ഒരുമിച്ച് ബാച്ച് ചെയ്യാൻ ശ്രമിക്കുമ്പോഴുള്ള എന്തെങ്കിലും പ്രശ്നമോ ആകാം. അല്ലെങ്കിൽ അത് മോഡൽ കോഡിലെയോ, നിങ്ങളുടെ ലോസ്സ് ഫംഗ്‌ഷനിലെയോ ഒപ്‌റ്റിമൈസറിലെയോ എന്തെങ്കിലും തകരാറാകാം. ട്രെയിനിംഗിൽ എല്ലാം ശരിയായി നടന്നാലും, നിങ്ങളുടെ മെട്രിക്കിൽ ഒരു പ്രശ്നമുണ്ടെങ്കിൽ ഇവാല്യുവേഷൻ സമയത്ത് എന്തെങ്കിലും പിഴയ്ക്കാം.

`model.fit()`-ൽ ഉണ്ടാകുന്ന ഒരു എറർ ഡീബഗ് ചെയ്യാനുള്ള ഏറ്റവും നല്ല മാർഗ്ഗം, എവിടെയാണ് കാര്യങ്ങൾ പിഴച്ചത് എന്ന് കാണാൻ ഈ മുഴുവൻ പൈപ്പ്‌ലൈനിലൂടെയും സ്വയം കടന്നുപോകുകയാണ്. അപ്പോൾ പലപ്പോഴും എറർ പരിഹരിക്കാൻ വളരെ എളുപ്പമാകും.

ഇത് കാണിക്കാൻ, [MNLI ഡേറ്റാസെറ്റിൽ](https://huggingface.co/datasets/glue) ഒരു DistilBERT മോഡൽ ഫൈൻ-ട്യൂൻ ചെയ്യാൻ (ശ്രമിക്കുന്ന) താഴെയുള്ള സ്‌ക്രിപ്‌റ്റ് നമ്മൾ ഉപയോഗിക്കും:

```py
from datasets import load_dataset
import evaluate
from transformers import (
    AutoTokenizer,
    TFAutoModelForSequenceClassification,
)

raw_datasets = load_dataset("glue", "mnli")

model_checkpoint = "distilbert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_checkpoint)


def preprocess_function(examples):
    return tokenizer(examples["premise"], examples["hypothesis"], truncation=True)


tokenized_datasets = raw_datasets.map(preprocess_function, batched=True)

train_dataset = tokenized_datasets["train"].to_tf_dataset(
    columns=["input_ids", "labels"], batch_size=16, shuffle=True
)

validation_dataset = tokenized_datasets["validation_matched"].to_tf_dataset(
    columns=["input_ids", "labels"], batch_size=16, shuffle=True
)

model = TFAutoModelForSequenceClassification.from_pretrained(model_checkpoint)

model.compile(loss="sparse_categorical_crossentropy", optimizer="adam")

model.fit(train_dataset)
```

ഇത് എക്‌സിക്യൂട്ട് ചെയ്യാൻ ശ്രമിച്ചാൽ, ഡേറ്റാസെറ്റ് കൺവേർഷൻ നടത്തുമ്പോൾ കുറച്ച് `VisibleDeprecationWarning`-കൾ കിട്ടിയേക്കാം -- ഇത് ഞങ്ങൾക്ക് അറിയാവുന്ന ഒരു UX പ്രശ്നമാണ്, അതിനാൽ അത് അവഗണിക്കുക. ഉദാഹരണത്തിന്, 2021 നവംബറിനു ശേഷം ഈ കോഴ്‌സ് വായിക്കുമ്പോഴും ഇത് സംഭവിക്കുന്നുണ്ടെങ്കിൽ, @carrigmat ഇത് ശരിയാക്കുന്നതുവരെ അദ്ദേഹത്തിന് ദേഷ്യം നിറഞ്ഞ ട്വീറ്റുകൾ അയയ്ക്കുക.

എന്നാൽ അതിലും ഗുരുതരമായ പ്രശ്നം, നമുക്ക് ഒരു പൂർണ്ണ എറർ കിട്ടുന്നു എന്നതാണ്. അതും ഭയപ്പെടുത്തുന്ന വിധം നീണ്ടത്:

```python out
ValueError: No gradients provided for any variable: ['tf_distil_bert_for_sequence_classification/distilbert/embeddings/word_embeddings/weight:0', '...']
```

ഇതിന്റെ അർത്ഥമെന്താണ്? നമ്മുടെ ഡേറ്റയിൽ ട്രെയിൻ ചെയ്യാൻ ശ്രമിച്ചു, പക്ഷേ ഗ്രേഡിയന്റ് ഒന്നും കിട്ടിയില്ല? ഇത് നന്നായി ആശയക്കുഴപ്പമുണ്ടാക്കുന്നു; ഇതുപോലൊന്ന് ഡീബഗ് ചെയ്യാൻ എവിടെ നിന്ന് തുടങ്ങും? കിട്ടുന്ന എറർ പ്രശ്നം എവിടെയാണെന്ന് ഉടനടി സൂചിപ്പിക്കുന്നില്ലെങ്കിൽ, ഓരോ ഘട്ടത്തിലും എല്ലാം ശരിയാണെന്ന് ഉറപ്പുവരുത്തിക്കൊണ്ട് കാര്യങ്ങളിലൂടെ ക്രമത്തിൽ കടന്നുപോകുകയാണ് പലപ്പോഴും ഏറ്റവും നല്ല പരിഹാരം. തീർച്ചയായും, തുടങ്ങേണ്ട സ്ഥലം എപ്പോഴും ഇതാണ്...

### നിങ്ങളുടെ ഡേറ്റ പരിശോധിക്കുക[[check-your-data]]

ഇത് പറയേണ്ട ആവശ്യമില്ല; പക്ഷേ നിങ്ങളുടെ ഡേറ്റ കേടായതാണെങ്കിൽ, Keras-ന് അത് നിങ്ങൾക്കായി ശരിയാക്കാൻ കഴിയില്ല. അതിനാൽ ആദ്യം ചെയ്യേണ്ടത്, നിങ്ങളുടെ ട്രെയിനിംഗ് സെറ്റിനുള്ളിൽ എന്താണുള്ളത് എന്ന് ഒന്ന് നോക്കുകയാണ്.

`raw_datasets`-ലും `tokenized_datasets`-ലും നോക്കാൻ തോന്നുമെങ്കിലും, ഡേറ്റ മോഡലിലേക്ക് കടക്കാൻ പോകുന്ന കൃത്യം സ്ഥലത്ത് അതിലേക്ക് പോകാൻ ഞങ്ങൾ ശക്തമായി ശുപാർശ ചെയ്യുന്നു. അതായത്, `to_tf_dataset()` ഫംഗ്‌ഷൻ ഉപയോഗിച്ച് നിങ്ങൾ ഉണ്ടാക്കിയ `tf.data.Dataset`-ൽ നിന്നുള്ള ഒരു ഔട്ട്‌പുട്ട് വായിക്കുക! അപ്പോൾ അത് എങ്ങനെ ചെയ്യും? `tf.data.Dataset` ഒബ്‌ജക്റ്റുകൾ ഒരു സമയം മുഴുവൻ ബാച്ചുകളാണ് നൽകുന്നത്, അവ ഇൻഡെക്‌സിംഗ് സപ്പോർട്ട് ചെയ്യുന്നുമില്ല; അതിനാൽ `train_dataset[0]` എന്ന് ചോദിക്കാൻ കഴിയില്ല. എന്നാൽ, മര്യാദയോടെ ഒരു ബാച്ച് ചോദിക്കാൻ നമുക്ക് കഴിയും:

```py
for batch in train_dataset:
    break
```

`break` ഒരു ഇറ്ററേഷന് ശേഷം ലൂപ്പ് അവസാനിപ്പിക്കുന്നു; അതിനാൽ ഇത് `train_dataset`-ൽ നിന്ന് വരുന്ന ആദ്യ ബാച്ച് എടുത്ത് `batch` ആയി സേവ് ചെയ്യുന്നു. ഇനി, അതിനുള്ളിൽ എന്താണുള്ളത് എന്ന് നോക്കാം:

ഇത് ശരിയാണെന്ന് തോന്നുന്നു, അല്ലേ? `labels`, `attention_mask`, `input_ids` എന്നിവ നമ്മൾ മോഡലിന് നൽകുന്നു; ഔട്ട്‌പുട്ടുകൾ കണക്കാക്കാനും ലോസ്സ് കണക്കാക്കാനും ആവശ്യമായതെല്ലാം അതിലുണ്ടാകണം. അപ്പോൾ എന്തുകൊണ്ട് നമുക്ക് ഗ്രേഡിയന്റ് ഇല്ല? സൂക്ഷിച്ചു നോക്കൂ: നമ്മൾ ഒരൊറ്റ ഡിക്‌ഷണറിയാണ് ഇൻപുട്ടായി നൽകുന്നത്; പക്ഷേ ഒരു ട്രെയിനിംഗ് ബാച്ച് സാധാരണയായി ഒരു ഇൻപുട്ട് ടെൻസറോ ഡിക്‌ഷണറിയോ, കൂടെ ഒരു ലേബൽ ടെൻസറും ആണ്. നമ്മുടെ ലേബലുകൾ ഇൻപുട്ട് ഡിക്‌ഷണറിയിലെ ഒരു കീ മാത്രമാണ്.

ഇത് ഒരു പ്രശ്നമാണോ? യഥാർത്ഥത്തിൽ എപ്പോഴുമല്ല! പക്ഷേ TensorFlow ഉപയോഗിച്ച് Transformer മോഡലുകൾ ട്രെയിൻ ചെയ്യുമ്പോൾ നിങ്ങൾ നേരിടുന്ന ഏറ്റവും സാധാരണമായ പ്രശ്നങ്ങളിൽ ഒന്നാണിത്. നമ്മുടെ മോഡലുകൾക്കെല്ലാം ആന്തരികമായി ലോസ്സ് കണക്കാക്കാൻ കഴിയും; പക്ഷേ അതിന് ലേബലുകൾ ഇൻപുട്ട് ഡിക്‌ഷണറിയിൽ നൽകേണ്ടതുണ്ട്. `compile()`-ന് ഒരു ലോസ്സ് മൂല്യം നമ്മൾ വ്യക്തമാക്കാത്തപ്പോൾ ഉപയോഗിക്കുന്ന ലോസ്സ് ഇതാണ്. മറുവശത്ത്, Keras സാധാരണയായി ലേബലുകൾ ഇൻപുട്ട് ഡിക്‌ഷണറിയിൽ നിന്ന് വേറിട്ട് നൽകുമെന്നാണ് പ്രതീക്ഷിക്കുന്നത്; അങ്ങനെ ചെയ്തില്ലെങ്കിൽ ലോസ്സ് കണക്കുകൂട്ടലുകൾ സാധാരണയായി പരാജയപ്പെടും.

ഇപ്പോൾ പ്രശ്നം കൂടുതൽ വ്യക്തമായി: നമ്മൾ ഒരു `loss` ആർഗ്യുമെന്റ് നൽകി — അതായത് ലോസ്സുകൾ കണക്കാക്കാൻ Keras-നോട് ആവശ്യപ്പെടുന്നു; പക്ഷേ ലേബലുകൾ മോഡലിലേക്കുള്ള ഇൻപുട്ടുകളായാണ് നൽകിയത്, Keras പ്രതീക്ഷിക്കുന്ന സ്ഥലത്ത് ലേബലുകളായല്ല! ഇവയിൽ ഒന്ന് നമ്മൾ തിരഞ്ഞെടുക്കണം: ഒന്നുകിൽ മോഡലിന്റെ ആന്തരിക ലോസ്സ് ഉപയോഗിച്ച് ലേബലുകൾ ഉള്ളിടത്തുതന്നെ വയ്ക്കുക; അല്ലെങ്കിൽ Keras ലോസ്സുകൾ ഉപയോഗിക്കുന്നത് തുടർന്ന്, ലേബലുകൾ Keras പ്രതീക്ഷിക്കുന്ന സ്ഥലത്തേക്ക് മാറ്റുക. ലളിതമാക്കാൻ, ആദ്യത്തെ വഴി സ്വീകരിക്കാം. `compile()` വിളി ഇങ്ങനെ മാറ്റുക:


Keras-ലെ ശരിക്കും മികച്ച ഒരു സൗകര്യ ഫംഗ്‌ഷനാണ് `model.fit()`; പക്ഷേ അത് നിങ്ങൾക്കായി ഒരുപാട് കാര്യങ്ങൾ ചെയ്യുന്നു, അതുകൊണ്ട് ഒരു പ്രശ്നം കൃത്യമായി എവിടെയാണ് സംഭവിച്ചത് എന്ന് കണ്ടെത്തുന്നത് കൂടുതൽ കുഴപ്പം പിടിച്ചതാകാം. നിങ്ങളുടെ മോഡൽ ഡീബഗ് ചെയ്യുകയാണെങ്കിൽ, ശരിക്കും സഹായിക്കുന്ന ഒരു തന്ത്രം, മോഡലിന് ഒരൊറ്റ ബാച്ച് മാത്രം നൽകി, ആ ബാച്ചിന്റെ ഔട്ട്‌പുട്ടുകൾ വിശദമായി നോക്കുകയാണ്. മോഡൽ എററുകൾ തരുന്നുണ്ടെങ്കിൽ ശരിക്കും സഹായകമായ മറ്റൊരു നുറുങ്ങ്, `run_eagerly=True` ഉപയോഗിച്ച് മോഡൽ `compile()` ചെയ്യുകയാണ്. ഇത് വളരെ വേഗത കുറയ്ക്കും; പക്ഷേ എറർ സന്ദേശങ്ങൾ കൂടുതൽ മനസ്സിലാക്കാവുന്നതാക്കും, കാരണം നിങ്ങളുടെ മോഡലിന്റെ കോഡിൽ കൃത്യമായി എവിടെയാണ് പ്രശ്നം സംഭവിച്ചത് എന്ന് അവ സൂചിപ്പിക്കും.

### നിങ്ങളുടെ ഹൈപ്പർപാരാമീറ്ററുകൾ പരിശോധിക്കുക[[check-your-hyperparameters]]

മുകളിലെ കോഡ് തിരിഞ്ഞു നോക്കിയാൽ, ഒരുപക്ഷേ `batch_size` ഒഴികെ ഹൈപ്പർപാരാമീറ്ററുകൾ ഒന്നും കാണാൻ കഴിഞ്ഞെന്നു വരില്ല; അത് കുറ്റക്കാരനാകാൻ സാധ്യതയുള്ളതായും തോന്നുന്നില്ല. പക്ഷേ വഞ്ചിതരാകരുത്; ഹൈപ്പർപാരാമീറ്ററുകൾ എപ്പോഴുമുണ്ട്, അവ കാണാൻ കഴിയുന്നില്ലെങ്കിൽ, അവ ഏത് മൂല്യത്തിലാണ് സെറ്റ് ചെയ്തിരിക്കുന്നത് എന്ന് നിങ്ങൾക്ക് അറിയില്ല എന്നു മാത്രമാണ് അർത്ഥം. പ്രത്യേകിച്ച്, Keras-നെക്കുറിച്ചുള്ള ഒരു നിർണ്ണായക കാര്യം ഓർക്കുക: ഒരു ലോസ്സോ ഒപ്‌റ്റിമൈസറോ ആക്റ്റിവേഷൻ ഫംഗ്‌ഷനോ ഒരു സ്‌ട്രിംഗ് ഉപയോഗിച്ച് സെറ്റ് ചെയ്താൽ, _അതിന്റെ എല്ലാ ആർഗ്യുമെന്റുകളും അവയുടെ ഡിഫോൾട്ട് മൂല്യങ്ങളിലേക്ക് സെറ്റ് ചെയ്യപ്പെടും_. അതായത്, ഇതിന് സ്‌ട്രിംഗുകൾ ഉപയോഗിക്കുന്നത് വളരെ സൗകര്യപ്രദമാണെങ്കിലും, അങ്ങനെ ചെയ്യുമ്പോൾ വളരെ ശ്രദ്ധിക്കണം; കാരണം അത് നിർണ്ണായകമായ കാര്യങ്ങൾ നിങ്ങളിൽ നിന്ന് എളുപ്പത്തിൽ മറയ്ക്കാം. (മുകളിലെ ഐച്ഛിക വെല്ലുവിളി പരീക്ഷിക്കുന്നവർ ഈ വസ്തുത നന്നായി ശ്രദ്ധിക്കണം.)

ഈ സന്ദർഭത്തിൽ, ഒരു സ്‌ട്രിംഗ് ഉപയോഗിച്ച് നമ്മൾ എവിടെയാണ് ഒരു ആർഗ്യുമെന്റ് സെറ്റ് ചെയ്തത്? തുടക്കത്തിൽ ലോസ്സ് ഒരു സ്‌ട്രിംഗ് ഉപയോഗിച്ചാണ് സെറ്റ് ചെയ്തിരുന്നത്; പക്ഷേ ഇപ്പോൾ അങ്ങനെ ചെയ്യുന്നില്ല. എന്നാൽ, ഒപ്‌റ്റിമൈസർ ഒരു സ്‌ട്രിംഗ് ഉപയോഗിച്ചാണ് നമ്മൾ സെറ്റ് ചെയ്യുന്നത്. അത് നമ്മിൽ നിന്ന് എന്തെങ്കിലും മറയ്ക്കുന്നുണ്ടാകുമോ? [അതിന്റെ ആർഗ്യുമെന്റുകൾ](https://www.tensorflow.org/api_docs/python/tf/keras/optimizers/Adam) ഒന്ന് നോക്കാം.

ഇവിടെ എന്തെങ്കിലും ശ്രദ്ധയിൽ പെടുന്നുണ്ടോ? അതെ -- ലേണിംഗ് റേറ്റ്! `'adam'` എന്ന സ്‌ട്രിംഗ് മാത്രം ഉപയോഗിക്കുമ്പോൾ, നമുക്ക് ഡിഫോൾട്ട് ലേണിംഗ് റേറ്റ് കിട്ടും, അതായത് 0.001 അഥവാ 1e-3. ഒരു Transformer മോഡലിന് ഇത് വളരെ കൂടുതലാണ്! പൊതുവെ, നിങ്ങളുടെ മോഡലുകൾക്ക് 1e-5-നും 1e-4-നും ഇടയിലുള്ള ലേണിംഗ് റേറ്റുകൾ പരീക്ഷിക്കാൻ ഞങ്ങൾ ശുപാർശ ചെയ്യുന്നു; ഇവിടെ നമ്മൾ യഥാർത്ഥത്തിൽ ഉപയോഗിക്കുന്ന മൂല്യത്തെക്കാൾ 10 മുതൽ 100 മടങ്ങ് വരെ ചെറുതാണത്. അത് ഒരു വലിയ പ്രശ്നമാകാമെന്ന് തോന്നുന്നു; അതിനാൽ അത് കുറയ്ക്കാൻ ശ്രമിക്കാം. അതിനായി, യഥാർത്ഥ `optimizer` ഒബ്‌ജക്റ്റ് ഇംപോർട്ട് ചെയ്യണം. അതോടൊപ്പം, ഉയർന്ന ലേണിംഗ് റേറ്റിലുള്ള ട്രെയിനിംഗ് വെയ്റ്റുകളെ കേടുവരുത്തിയിട്ടുണ്ടെങ്കിൽ എന്നു കരുതി, ചെക്ക്‌പോയിന്റിൽ നിന്ന് മോഡൽ വീണ്ടും ഇനിഷ്യലൈസ് ചെയ്യാം:

```python
from tensorflow.keras.optimizers import Adam

model = TFAutoModelForSequenceClassification.from_pretrained(model_checkpoint)
model.compile(optimizer=Adam(5e-5))
```

> [!TIP]
> 💡 🤗 Transformers-ൽ നിന്ന് `create_optimizer()` ഫംഗ്‌ഷനും ഇംപോർട്ട് ചെയ്യാം; ശരിയായ വെയ്റ്റ് ഡീകേയും (weight decay) ലേണിംഗ് റേറ്റ് വാം-അപ്പും ഡീകേയും ഉള്ള ഒരു AdamW ഒപ്‌റ്റിമൈസർ അത് നിങ്ങൾക്ക് തരും. ഡിഫോൾട്ട് Adam ഒപ്‌റ്റിമൈസർ ഉപയോഗിച്ച് കിട്ടുന്നതിനെക്കാൾ അൽപ്പം മെച്ചപ്പെട്ട ഫലങ്ങൾ ഈ ഒപ്‌റ്റിമൈസർ പലപ്പോഴും തരും.

ഇനി, പുതിയ, മെച്ചപ്പെട്ട ലേണിംഗ് റേറ്റ് ഉപയോഗിച്ച് മോഡൽ ഫിറ്റ് ചെയ്യാൻ ശ്രമിക്കാം:

```python
model.fit(train_dataset)
```

ഇപ്പോൾ നമ്മുടെ ലോസ്സ് ശരിക്കും എങ്ങോട്ടോ നീങ്ങുന്നു! ഒടുവിൽ ട്രെയിനിംഗ് പ്രവർത്തിക്കുന്നതായി തോന്നുന്നു. ഇവിടെ ഒരു പാഠമുണ്ട്: നിങ്ങളുടെ മോഡൽ ഓടുന്നുണ്ട്, പക്ഷേ ലോസ്സ് കുറയുന്നില്ല, ഡേറ്റ ശരിയാണെന്ന് ഉറപ്പുമാണ് എങ്കിൽ, ലേണിംഗ് റേറ്റ്, വെയ്റ്റ് ഡീകേ പോലുള്ള ഹൈപ്പർപാരാമീറ്ററുകൾ പരിശോധിക്കുന്നത് നല്ലൊരു ആശയമാണ്. ഇവയിൽ ഏതെങ്കിലും വളരെ ഉയർന്നതായി സെറ്റ് ചെയ്താൽ, ഉയർന്ന ഒരു ലോസ്സ് മൂല്യത്തിൽ ട്രെയിനിംഗ് "നിലച്ചുപോകാൻ" വളരെ സാധ്യതയുണ്ട്.

## മറ്റ് സാധ്യമായ പ്രശ്നങ്ങൾ[[other-potential-issues]]

മുകളിലെ സ്‌ക്രിപ്‌റ്റിലെ പ്രശ്നങ്ങൾ നമ്മൾ കൈകാര്യം ചെയ്തു; പക്ഷേ നിങ്ങൾ നേരിടാവുന്ന മറ്റ് പല സാധാരണ എററുകളുമുണ്ട്. (വളരെ അപൂർണ്ണമായ) ഒരു പട്ടിക നോക്കാം.

### out-of-memory എററുകൾ കൈകാര്യം ചെയ്യുന്നു[[dealing-with-out-of-memory-errors]]

മെമ്മറി തീരുന്നതിന്റെ വ്യക്തമായ അടയാളം "OOM when allocating tensor" പോലുള്ള ഒരു എററാണ് -- OOM എന്നത് "out of memory" എന്നതിന്റെ ചുരുക്കമാണ്. ലാർജ് ലാംഗ്വേജ് മോഡലുകളുമായി പ്രവർത്തിക്കുമ്പോഴുള്ള വളരെ സാധാരണമായ ഒരു അപകടമാണിത്. ഇത് നേരിട്ടാൽ, ബാച്ച് സൈസ് പകുതിയാക്കി വീണ്ടും ശ്രമിക്കുന്നതാണ് നല്ലൊരു തന്ത്രം. എന്നാൽ, ചില മോഡലുകൾ *വളരെ* വലുതാണെന്ന് ഓർക്കുക. ഉദാഹരണത്തിന്, പൂർണ്ണ വലുപ്പത്തിലുള്ള GPT-2-ന് 1.5B പാരാമീറ്ററുകളുണ്ട്; അതായത് മോഡൽ സൂക്ഷിക്കാൻ മാത്രം 6 GB മെമ്മറിയും, അതിന്റെ ഗ്രേഡിയന്റുകൾക്ക് വേറെ 6 GB-യും വേണ്ടിവരും! പൂർണ്ണ GPT-2 മോഡൽ ട്രെയിൻ ചെയ്യാൻ, ഏത് ബാച്ച് സൈസ് ഉപയോഗിച്ചാലും സാധാരണയായി 20 GB-യിൽ കൂടുതൽ VRAM വേണ്ടിവരും; അത് ഏതാനും GPU-കൾക്ക് മാത്രമേയുള്ളൂ. `distilbert-base-cased` പോലുള്ള ഭാരം കുറഞ്ഞ മോഡലുകൾ റൺ ചെയ്യാൻ വളരെ എളുപ്പമാണ്, അവ വളരെ വേഗത്തിൽ ട്രെയിൻ ആവുകയും ചെയ്യും.

> [!TIP]
> കോഴ്‌സിന്റെ അടുത്ത ഭാഗത്തിൽ, മെമ്മറി ഉപയോഗം കുറയ്ക്കാനും ഏറ്റവും വലിയ മോഡലുകൾ ഫൈൻ-ട്യൂൻ ചെയ്യാനും സഹായിക്കുന്ന കൂടുതൽ വിപുലമായ രീതികൾ നമ്മൾ പരിശോധിക്കും.

### വിശപ്പു മാറാത്ത TensorFlow 🦛[[hungry-hungry-tensorflow]]

നിങ്ങൾ അറിഞ്ഞിരിക്കേണ്ട TensorFlow-ന്റെ ഒരു പ്രത്യേക സ്വഭാവം, ഒരു മോഡൽ ലോഡ് ചെയ്യുകയോ എന്തെങ്കിലും ട്രെയിനിംഗ് നടത്തുകയോ ചെയ്യുമ്പോൾ തന്നെ, നിങ്ങളുടെ GPU മെമ്മറി *മുഴുവനും* അത് സ്വയം അലോക്കേറ്റ് ചെയ്യുന്നു, പിന്നീട് ആവശ്യാനുസരണം ആ മെമ്മറി വിഭജിക്കുന്നു എന്നതാണ്. PyTorch പോലുള്ള മറ്റ് ഫ്രെയിംവർക്കുകളുടെ സ്വഭാവത്തിൽ നിന്ന് ഇത് വ്യത്യസ്തമാണ്; അവ ആന്തരികമായി ചെയ്യുന്നതിനു പകരം CUDA ഉപയോഗിച്ച് ആവശ്യാനുസരണം മെമ്മറി അലോക്കേറ്റ് ചെയ്യുന്നു. TensorFlow-ന്റെ സമീപനത്തിന്റെ ഒരു ഗുണം, മെമ്മറി തീരുമ്പോൾ ഉപകാരപ്രദമായ എററുകൾ പലപ്പോഴും തരാൻ അതിന് കഴിയും, മുഴുവൻ CUDA കേർണലും തകർക്കാതെ ആ അവസ്ഥയിൽ നിന്ന് കരകയറാനും കഴിയും എന്നതാണ്. പക്ഷേ ഒരു പ്രധാന ദോഷവുമുണ്ട്: ഒരേ സമയം രണ്ട് TensorFlow പ്രോസസ്സുകൾ റൺ ചെയ്താൽ, **നിങ്ങൾക്ക് കഷ്ടകാലമായിരിക്കും**.

Colab-ൽ റൺ ചെയ്യുകയാണെങ്കിൽ ഇതിനെക്കുറിച്ച് ആശങ്കപ്പെടേണ്ട; പക്ഷേ ലോക്കലായി റൺ ചെയ്യുകയാണെങ്കിൽ ഇത് തീർച്ചയായും ശ്രദ്ധിക്കേണ്ട കാര്യമാണ്. പ്രത്യേകിച്ച്, ഒരു നോട്ട്‌ബുക്ക് ടാബ് അടയ്ക്കുന്നത് ആ നോട്ട്‌ബുക്ക് ഷട്ട് ഡൗൺ ചെയ്യണമെന്നില്ല എന്ന് ഓർക്കുക! ഓടിക്കൊണ്ടിരിക്കുന്ന നോട്ട്‌ബുക്കുകൾ (പച്ച ഐക്കൺ ഉള്ളവ) തിരഞ്ഞെടുത്ത്, ഡയറക്ടറി ലിസ്‌റ്റിംഗിൽ നിന്ന് അവ സ്വയം ഷട്ട് ഡൗൺ ചെയ്യേണ്ടിവന്നേക്കാം. TensorFlow ഉപയോഗിച്ചിരുന്ന, ഓടിക്കൊണ്ടിരിക്കുന്ന ഏതൊരു നോട്ട്‌ബുക്കും നിങ്ങളുടെ GPU മെമ്മറിയുടെ വലിയൊരു ഭാഗം ഇപ്പോഴും പിടിച്ചുവച്ചിരിക്കാം; അതായത് നിങ്ങൾ തുടങ്ങുന്ന ഏതൊരു പുതിയ നോട്ട്‌ബുക്കിനും വളരെ വിചിത്രമായ പ്രശ്നങ്ങൾ നേരിടേണ്ടിവരാം.

മുമ്പ് പ്രവർത്തിച്ചിരുന്ന കോഡിൽ CUDA, BLAS, അല്ലെങ്കിൽ cuBLAS സംബന്ധിച്ച എററുകൾ കിട്ടിത്തുടങ്ങിയാൽ, പലപ്പോഴും കുറ്റക്കാരൻ ഇതാണ്. പരിശോധിക്കാൻ `nvidia-smi` പോലുള്ള ഒരു കമാൻഡ് ഉപയോഗിക്കാം -- നിലവിലെ നോട്ട്‌ബുക്ക് ഷട്ട് ഡൗൺ ചെയ്യുകയോ റീസ്‌റ്റാർട്ട് ചെയ്യുകയോ ചെയ്യുമ്പോൾ, നിങ്ങളുടെ മെമ്മറിയുടെ ഭൂരിഭാഗവും സ്വതന്ത്രമാണോ, അതോ ഇപ്പോഴും ഉപയോഗത്തിലാണോ? ഇപ്പോഴും ഉപയോഗത്തിലാണെങ്കിൽ, മറ്റെന്തോ അത് പിടിച്ചുവച്ചിരിക്കുന്നു!


### നിങ്ങളുടെ ഡേറ്റ പരിശോധിക്കുക (വീണ്ടും!)[[check-your-data-again]]

നിങ്ങളുടെ ഡേറ്റയിൽ നിന്ന് എന്തെങ്കിലും പഠിക്കാൻ ശരിക്കും സാധ്യമാണെങ്കിൽ മാത്രമേ നിങ്ങളുടെ മോഡൽ എന്തെങ്കിലും പഠിക്കൂ. ഡേറ്റയെ കേടുവരുത്തുന്ന ഒരു ബഗ് ഉണ്ടെങ്കിലോ, ലേബലുകൾ ക്രമരഹിതമായി നൽകിയിട്ടുണ്ടെങ്കിലോ, നിങ്ങളുടെ ഡേറ്റാസെറ്റിൽ ഒരു മോഡലും ട്രെയിൻ ആകാതിരിക്കാൻ വളരെ സാധ്യതയുണ്ട്. ഇവിടെ ഉപകാരപ്രദമായ ഒരു ടൂളാണ് `tokenizer.decode()`. ഇത് `input_ids`-നെ തിരികെ സ്‌ട്രിംഗുകളാക്കി മാറ്റും; അങ്ങനെ ഡേറ്റ കണ്ട്, നിങ്ങളുടെ ട്രെയിനിംഗ് ഡേറ്റ പഠിപ്പിക്കാൻ ഉദ്ദേശിക്കുന്നത് തന്നെയാണോ പഠിപ്പിക്കുന്നത് എന്ന് കാണാം. ഉദാഹരണത്തിന്, മുകളിൽ ചെയ്തതുപോലെ നിങ്ങളുടെ `tf.data.Dataset`-ൽ നിന്ന് ഒരു `batch` കിട്ടിയ ശേഷം, ആദ്യ എലമെന്റ് ഇങ്ങനെ ഡീകോഡ് ചെയ്യാം:

```py
input_ids = batch["input_ids"].numpy()
tokenizer.decode(input_ids[0])
```

തുടർന്ന്, അത് ആദ്യ ലേബലുമായി ഇങ്ങനെ താരതമ്യം ചെയ്യാം:

```py
labels = batch["labels"].numpy()
label = labels[0]
```

ഇങ്ങനെ നിങ്ങളുടെ ഡേറ്റ കാണാൻ കഴിഞ്ഞാൽ, സ്വയം ഈ ചോദ്യങ്ങൾ ചോദിക്കാം:

- ഡീകോഡ് ചെയ്ത ഡേറ്റ മനസ്സിലാക്കാവുന്നതാണോ?
- ലേബലുകളോട് നിങ്ങൾ യോജിക്കുന്നുണ്ടോ?
- മറ്റുള്ളവയെക്കാൾ കൂടുതൽ സാധാരണമായ ഒരു ലേബൽ ഉണ്ടോ?
- മോഡൽ ക്രമരഹിതമായ ഒരു ഉത്തരം / എപ്പോഴും ഒരേ ഉത്തരം പ്രവചിച്ചാൽ ലോസ്സ്/മെട്രിക് എന്തായിരിക്കണം?

ഡേറ്റ നോക്കിയതിനു ശേഷം, മോഡലിന്റെ ഏതാനും പ്രവചനങ്ങളിലൂടെ കടന്നുപോകുക -- നിങ്ങളുടെ മോഡൽ ടോക്കണുകളാണ് ഔട്ട്‌പുട്ട് ചെയ്യുന്നതെങ്കിൽ, അവയും ഡീകോഡ് ചെയ്തു നോക്കുക! മോഡൽ എപ്പോഴും ഒരേ കാര്യമാണ് പ്രവചിക്കുന്നതെങ്കിൽ, നിങ്ങളുടെ ഡേറ്റാസെറ്റ് ഒരു കാറ്റഗറിയിലേക്ക് ചായ്‌വുള്ളതാകാം (ക്ലാസിഫിക്കേഷൻ പ്രശ്നങ്ങളിൽ); അതിനാൽ അപൂർവ്വ ക്ലാസ്സുകൾ ഓവർസാമ്പിൾ ചെയ്യുന്നതു പോലുള്ള രീതികൾ സഹായിക്കാം. അല്ലെങ്കിൽ, മോശം ഹൈപ്പർപാരാമീറ്റർ ക്രമീകരണങ്ങൾ പോലുള്ള ട്രെയിനിംഗ് പ്രശ്നങ്ങളും ഇതിന് കാരണമാകാം.

ട്രെയിനിംഗിനു മുമ്പുള്ള നിങ്ങളുടെ പ്രാരംഭ മോഡലിൽ കിട്ടുന്ന ലോസ്സ്/മെട്രിക്, ക്രമരഹിത പ്രവചനങ്ങൾക്ക് പ്രതീക്ഷിക്കുന്ന ലോസ്സ്/മെട്രിക്കിൽ നിന്ന് വളരെ വ്യത്യസ്തമാണെങ്കിൽ, ലോസ്സോ മെട്രിക്കോ കണക്കാക്കുന്ന രീതി ഒന്നുകൂടി പരിശോധിക്കുക; അവിടെ ഒരു ബഗ് ഉണ്ടാകാൻ സാധ്യതയുണ്ട്. അവസാനം കൂട്ടിച്ചേർക്കുന്ന പല ലോസ്സുകൾ ഉപയോഗിക്കുകയാണെങ്കിൽ, അവ ഒരേ സ്‌കെയിലിലാണെന്ന് ഉറപ്പുവരുത്തുക.

നിങ്ങളുടെ ഡേറ്റ പെർഫെക്റ്റാണെന്ന് ഉറപ്പായാൽ, ഒരു ലളിതമായ ടെസ്‌റ്റിലൂടെ മോഡലിന് അതിൽ ട്രെയിൻ ആകാൻ കഴിവുണ്ടോ എന്ന് നോക്കാം.

### ഒരു ബാച്ചിൽ നിങ്ങളുടെ മോഡൽ ഓവർഫിറ്റ് ചെയ്യുക[[overfit-your-model-on-one-batch]]

ട്രെയിൻ ചെയ്യുമ്പോൾ സാധാരണയായി നമ്മൾ ഒഴിവാക്കാൻ ശ്രമിക്കുന്ന ഒന്നാണ് ഓവർഫിറ്റിംഗ്; കാരണം, നമ്മൾ ആഗ്രഹിക്കുന്ന പൊതു സവിശേഷതകൾ തിരിച്ചറിയാൻ പഠിക്കുന്നതിനു പകരം, മോഡൽ ട്രെയിനിംഗ് സാമ്പിളുകൾ കാണാതെ പഠിക്കുക മാത്രമാണ് ചെയ്യുന്നത് എന്നാണ് അതിന്റെ അർത്ഥം. എന്നിരുന്നാലും, ഒരേ ബാച്ചിൽ വീണ്ടും വീണ്ടും മോഡൽ ട്രെയിൻ ചെയ്യാൻ ശ്രമിക്കുന്നത്, നിങ്ങൾ രൂപപ്പെടുത്തിയ പ്രശ്നം, ട്രെയിൻ ചെയ്യാൻ ശ്രമിക്കുന്ന മോഡലിന് പരിഹരിക്കാൻ കഴിയുമോ എന്ന് പരിശോധിക്കാനുള്ള ഒരു നല്ല ടെസ്‌റ്റാണ്. നിങ്ങളുടെ പ്രാരംഭ ലേണിംഗ് റേറ്റ് വളരെ കൂടുതലാണോ എന്ന് കാണാനും ഇത് സഹായിക്കും.

നിങ്ങളുടെ `model` നിർവ്വചിച്ചു കഴിഞ്ഞാൽ ഇത് ചെയ്യുന്നത് വളരെ എളുപ്പമാണ്; ഒരു ബാച്ച് ട്രെയിനിംഗ് ഡേറ്റ എടുത്ത്, ആ `batch`-നെ നിങ്ങളുടെ മുഴുവൻ ഡേറ്റാസെറ്റായി കണക്കാക്കി, ധാരാളം എപ്പോക്കുകൾ അതിൽ ഫിറ്റ് ചെയ്യുക:

```py
for batch in train_dataset:
    break

# Make sure you have run model.compile() and set your optimizer,
# and your loss/metrics if you're using them

model.fit(batch, epochs=20)
```

> [!TIP]
> 💡 നിങ്ങളുടെ ട്രെയിനിംഗ് ഡേറ്റ അസന്തുലിതമാണെങ്കിൽ, എല്ലാ ലേബലുകളും അടങ്ങിയ ഒരു ബാച്ച് ട്രെയിനിംഗ് ഡേറ്റ ഉണ്ടാക്കാൻ ഉറപ്പുവരുത്തുക.

കിട്ടുന്ന മോഡലിന് അതേ `batch`-ൽ ഏകദേശം പെർഫെക്റ്റായ ഫലങ്ങൾ ഉണ്ടാകണം; ലോസ്സ് വേഗത്തിൽ 0-ലേക്ക് (അല്ലെങ്കിൽ നിങ്ങൾ ഉപയോഗിക്കുന്ന ലോസ്സിന്റെ ഏറ്റവും കുറഞ്ഞ മൂല്യത്തിലേക്ക്) താഴണം.

ഇതുപോലെ പെർഫെക്റ്റായ ഫലങ്ങൾ നേടാൻ നിങ്ങളുടെ മോഡലിന് കഴിയുന്നില്ലെങ്കിൽ, പ്രശ്നം രൂപപ്പെടുത്തിയ രീതിയിലോ ഡേറ്റയിലോ എന്തോ കുഴപ്പമുണ്ട് എന്നാണ് അതിനർത്ഥം; അതിനാൽ അത് ശരിയാക്കണം. ഓവർഫിറ്റിംഗ് ടെസ്‌റ്റ് പാസ്സാകാൻ കഴിഞ്ഞാൽ മാത്രമേ, നിങ്ങളുടെ മോഡലിന് ശരിക്കും എന്തെങ്കിലും പഠിക്കാൻ കഴിയുമെന്ന് ഉറപ്പിക്കാനാവൂ.

> [!WARNING]
> ⚠️ ഈ ഓവർഫിറ്റിംഗ് ടെസ്‌റ്റിനു ശേഷം നിങ്ങളുടെ മോഡൽ വീണ്ടും ഉണ്ടാക്കി വീണ്ടും കംപൈൽ ചെയ്യേണ്ടിവരും; കാരണം കിട്ടിയ മോഡലിന്, തിരിച്ചുവന്ന് നിങ്ങളുടെ മുഴുവൻ ഡേറ്റാസെറ്റിൽ ഉപകാരപ്രദമായ എന്തെങ്കിലും പഠിക്കാൻ കഴിയാൻ വഴിയില്ല.

### ആദ്യത്തെ ഒരു ബേസ്‌ലൈൻ കിട്ടുന്നതുവരെ ഒന്നും ട്യൂൺ ചെയ്യരുത്[[dont-tune-anything-until-you-have-a-first-baseline]]

തീവ്രമായ ഹൈപ്പർപാരാമീറ്റർ ട്യൂണിംഗ് മെഷീൻ ലേണിംഗിലെ ഏറ്റവും കഠിനമായ ഭാഗമാണെന്ന് എപ്പോഴും ഊന്നിപ്പറയാറുണ്ട്; പക്ഷേ മെട്രിക്കിൽ കുറച്ച് നേട്ടം കൂടി കിട്ടാൻ സഹായിക്കുന്ന അവസാന ഘട്ടം മാത്രമാണത്. ഒരു Transformer മോഡലിനൊപ്പം 1e-3 എന്ന ഡിഫോൾട്ട് Adam ലേണിംഗ് റേറ്റ് ഉപയോഗിക്കുന്നതു പോലുള്ള *വളരെ* മോശം ഹൈപ്പർപാരാമീറ്റർ മൂല്യങ്ങൾ, തീർച്ചയായും പഠനം വളരെ പതുക്കെയാക്കുകയോ പൂർണ്ണമായും നിലയ്ക്കുകയോ ചെയ്യും; പക്ഷേ മിക്കപ്പോഴും, 1e-5 മുതൽ 5e-5 വരെയുള്ള ലേണിംഗ് റേറ്റ് പോലുള്ള "ന്യായമായ" ഹൈപ്പർപാരാമീറ്ററുകൾ നല്ല ഫലങ്ങൾ തരാൻ ധാരാളം മതിയാകും. അതിനാൽ, നിങ്ങളുടെ ഡേറ്റാസെറ്റിലെ ബേസ്‌ലൈനിനെ മറികടക്കുന്ന എന്തെങ്കിലും കിട്ടുന്നതുവരെ, സമയമെടുക്കുന്നതും ചെലവേറിയതുമായ ഒരു ഹൈപ്പർപാരാമീറ്റർ തിരച്ചിലിലേക്ക് എടുത്തുചാടരുത്.

മതിയായ നല്ലൊരു മോഡൽ കിട്ടിയാൽ, കുറച്ച് മാറ്റങ്ങൾ വരുത്തിത്തുടങ്ങാം. വ്യത്യസ്ത ഹൈപ്പർപാരാമീറ്ററുകളോടെ ആയിരം റണ്ണുകൾ തുടങ്ങാൻ ശ്രമിക്കരുത്; പകരം, ഏതിനാണ് ഏറ്റവും വലിയ സ്വാധീനം എന്ന് മനസ്സിലാക്കാൻ, ഒരു ഹൈപ്പർപാരാമീറ്ററിന്റെ വ്യത്യസ്ത മൂല്യങ്ങളോടെ രണ്ട് റണ്ണുകൾ താരതമ്യം ചെയ്യുക.

മോഡലിൽ തന്നെ മാറ്റങ്ങൾ വരുത്തുകയാണെങ്കിൽ, അത് ലളിതമായി വയ്ക്കുക; ന്യായമായി വിശദീകരിക്കാൻ കഴിയാത്ത ഒന്നും പരീക്ഷിക്കരുത്. നിങ്ങളുടെ മാറ്റത്തിന് ഉദ്ദേശിക്കാത്ത ഫലങ്ങളൊന്നും ഉണ്ടായിട്ടില്ലെന്ന് ഉറപ്പുവരുത്താൻ, എപ്പോഴും ഓവർഫിറ്റിംഗ് ടെസ്‌റ്റിലേക്ക് തിരിച്ചു പോകാൻ ഉറപ്പുവരുത്തുക.

### സഹായം ചോദിക്കുക[[ask-for-help]]

നിങ്ങളുടെ പ്രശ്നം പരിഹരിക്കാൻ സഹായിച്ച ചില ഉപദേശങ്ങൾ ഈ ഭാഗത്തിൽ നിങ്ങൾ കണ്ടെത്തിയിട്ടുണ്ടാവുമെന്ന് പ്രതീക്ഷിക്കുന്നു; അങ്ങനെയല്ലെങ്കിൽ, [ഫോറങ്ങളിൽ](https://discuss.huggingface.co/) കമ്മ്യൂണിറ്റിയോട് എപ്പോഴും ചോദിക്കാമെന്ന് ഓർക്കുക. 

സഹായകമായേക്കാവുന്ന ചില അധിക റിസോഴ്‌സുകൾ ഇതാ:

- Joel Grus-ന്റെ ["Reproducibility as a vehicle for engineering best practices"](https://docs.google.com/presentation/d/1yHLPvPhUs2KGI5ZWo0sU-PKU3GimAk3iTsI38Z-B5Gw/edit#slide=id.p)
- Cecelia Shao-യുടെ ["Checklist for debugging neural networks"](https://towardsdatascience.com/checklist-for-debugging-neural-networks-d8b2a9434f21)
- Chase Roberts-ന്റെ ["How to unit test machine learning code"](https://medium.com/@keeper6928/how-to-unit-test-machine-learning-code-57cf6fd81765)
- Andrej Karpathy-യുടെ ["A Recipe for Training Neural Networks"](http://karpathy.github.io/2019/04/25/recipe/)

# Despliegue de inferencia optimizado

En esta sección, exploraremos frameworks avanzados para optimizar los despliegues de LLMs: Text Generation Inference (TGI), vLLM y llama.cpp. Estas aplicaciones se utilizan principalmente en entornos de producción para servir LLMs a usuarios. Esta sección se enfoca en cómo desplegar estos frameworks en producción en lugar de cómo usarlos para inferencia en una sola máquina.

Cubriremos cómo estas herramientas maximizan la eficiencia de la inferencia y simplifican los despliegues en producción de modelos de lenguaje grandes (Large Language Models).

## Guía de selección de frameworks

TGI, vLLM y llama.cpp cumplen propósitos similares pero tienen características distintas que los hacen más adecuados para diferentes casos de uso. Veamos las diferencias clave entre ellos, centrándonos en el rendimiento y la integración.

### Gestión de memoria y rendimiento

**TGI** está diseñado para ser estable y predecible en producción, utilizando longitudes de secuencia fijas para mantener el uso de memoria consistente. TGI gestiona la memoria utilizando técnicas de Flash Attention 2 y batching continuo (*continuous batching*). Esto significa que puede procesar cálculos de atención de manera muy eficiente y mantener la GPU ocupada alimentándola constantemente con trabajo. El sistema puede mover partes del modelo entre CPU y GPU cuando sea necesario, lo que ayuda a manejar modelos más grandes. 

<img src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/tgi/flash-attn.png" alt="Flash Attention" />

<Tip title="Cómo funciona Flash Attention">

Flash Attention es una técnica que optimiza el mecanismo de atención en modelos transformer al abordar los cuellos de botella del ancho de banda de la memoria. Como vimos anteriormente en el [Capítulo 1.8](/course/chapter1/8), el mecanismo de atención tiene una complejidad y un uso de memoria cuadráticos, lo que lo hace ineficiente para secuencias largas.

La innovación clave radica en cómo gestiona las transferencias de memoria entre la memoria de alto ancho de banda (High Bandwidth Memory o HBM) y la memoria caché SRAM, que es más rápida. La atención tradicional transfiere repetidamente datos entre HBM y SRAM, creando cuellos de botella al dejar la GPU inactiva. Flash Attention carga los datos una sola vez en SRAM y realiza todos los cálculos allí, minimizando las costosas transferencias de memoria. 

Si bien los beneficios son más significativos durante el entrenamiento, el menor uso de VRAM y la mayor eficiencia de Flash Attention también lo hacen muy valioso para la inferencia, permitiendo servir LLMs de forma más rápida y escalable.

</Tip>

**vLLM** adopta un enfoque diferente al utilizar PagedAttention. De manera similar a cómo una computadora gestiona su memoria mediante páginas, vLLM divide la memoria del modelo en bloques más pequeños. Este ingenioso sistema permite manejar solicitudes de diferentes tamaños con mayor flexibilidad y sin desperdiciar espacio de memoria. Es particularmente eficaz compartiendo memoria entre distintas solicitudes y reduce la fragmentación de la memoria, lo que hace que todo el sistema sea más eficiente.

<Tip title="Cómo funciona PagedAttention">

PagedAttention es una técnica que aborda otro cuello de botella crítico en la inferencia de LLMs: la gestión de la memoria del caché KV (*KV cache*). Como se discutió en el [Capítulo 1.8](/course/chapter1/8), durante la generación de texto, el modelo almacena las claves y valores de atención (caché KV) para cada token generado para reducir cálculos redundantes. El caché KV puede volverse gigantesco, especialmente con secuencias largas o múltiples solicitudes concurrentes.

La innovación clave de vLLM radica en cómo gestiona este caché:

1. **Paginación de memoria**: En lugar de tratar el caché KV como un único bloque grande, se divide en "páginas" de tamaño fijo (similar a la memoria virtual en los sistemas operativos).
2. **Almacenamiento no contiguo**: Las páginas no necesitan almacenarse de forma contigua en la memoria de la GPU, lo que permite una asignación de memoria más flexible.
3. **Gestión de la tabla de páginas**: Una tabla de páginas realiza un seguimiento de qué páginas pertenecen a qué secuencia, lo que permite una búsqueda y acceso eficientes.
4. **Memoria compartida**: Para operaciones como el muestreo paralelo, las páginas que almacenan el caché KV para el prompt pueden compartirse entre múltiples secuencias.

El enfoque de PagedAttention puede permitir un rendimiento hasta 24 veces mayor en comparación con los métodos tradicionales, convirtiéndolo en un cambio radical para los despliegues de LLMs en producción. Si deseas profundizar en cómo funciona PagedAttention, puedes leer la [guía de la documentación de vLLM](https://docs.vllm.ai/en/latest/design/kernel/paged_attention.html).

</Tip>

**llama.cpp** es una implementación en C/C++ altamente optimizada, diseñada originalmente para ejecutar modelos LLaMA en hardware de consumo. Se enfoca en la eficiencia en CPU con aceleración opcional en GPU y es ideal para entornos con recursos limitados. llama.cpp utiliza técnicas de cuantización para reducir el tamaño del modelo y los requisitos de memoria mientras mantiene un buen rendimiento. Implementa kernels optimizados para varias arquitecturas de CPU y admite la gestión básica del caché KV para una generación eficiente de tokens.

<Tip title="Cómo funciona la cuantización en llama.cpp">

La cuantización en llama.cpp reduce la precisión de los pesos del modelo de punto flotante de 32 o 16 bits a formatos de menor precisión como enteros de 8 bits (INT8), 4 bits o incluso menos. Esto reduce significativamente el uso de memoria y mejora la velocidad de inferencia con una pérdida mínima de calidad.

Las características clave de la cuantización en llama.cpp incluyen:
1. **Múltiples niveles de cuantización**: Admite cuantización de 8 bits, 4 bits, 3 bits e incluso 2 bits
2. **Formato GGML/GGUF**: Utiliza formatos de tensores personalizados optimizados para inferencia cuantizada
3. **Precisión mixta**: Puede aplicar diferentes niveles de cuantización a distintas partes del modelo
4. **Optimizaciones específicas del hardware**: Incluye rutas de código optimizadas para varias arquitecturas de CPU (AVX2, AVX-512, NEON)

Este enfoque permite ejecutar modelos de miles de millones de parámetros en hardware de consumo con memoria limitada, haciéndolo perfecto para despliegues locales y dispositivos de borde (*edge devices*).

</Tip>

### Despliegue e integración

Pasemos a las diferencias de despliegue e integración entre los frameworks.

**TGI** sobresale en despliegues a nivel empresarial gracias a sus características listas para producción. Incluye soporte integrado para Kubernetes y contiene todo lo necesario para ejecutarse en producción, como monitorización a través de Prometheus y Grafana, escalado automático y completas funciones de seguridad. El sistema también incluye registro (*logging*) de nivel empresarial y varias medidas de protección como filtrado de contenido y limitación de tasa (*rate limiting*) para mantener tu despliegue seguro y estable.

**vLLM** adopta un enfoque más flexible y amigable para desarrolladores. Está construido con Python en su núcleo y puede reemplazar fácilmente la API de OpenAI en tus aplicaciones existentes. El framework se enfoca en ofrecer el máximo rendimiento bruto y puede personalizarse para adaptarse a tus necesidades específicas. Funciona especialmente bien con Ray para gestionar clústeres, lo que lo convierte en una excelente opción cuando necesitas alto rendimiento y adaptabilidad.

**llama.cpp** prioriza la simplicidad y la portabilidad. Su implementación de servidor es ligera y puede ejecutarse en una amplia gama de hardware, desde potentes servidores hasta portátiles de consumo e incluso algunos dispositivos móviles de alta gama. Con dependencias mínimas y un núcleo simple de C/C++, es fácil de desplegar en entornos donde instalar frameworks de Python sería complicado. El servidor proporciona una API compatible con OpenAI a la vez que mantiene una huella de recursos mucho menor que otras soluciones.

<hfoption value="tgi" label="TGI">

TGI es fácil de instalar y usar, con una profunda integración en el ecosistema de Hugging Face.

Primero, inicia el servidor TGI usando Docker:

```sh
docker run --gpus all \
    --shm-size 1g \
    -p 8080:80 \
    -v ~/.cache/huggingface:/data \
    ghcr.io/huggingface/text-generation-inference:latest \
    --model-id HuggingFaceTB/SmolLM2-360M-Instruct
```

Luego interactúa con él utilizando el `InferenceClient` de Hugging Face:

```python
from huggingface_hub import InferenceClient

# Inicializar cliente apuntando al endpoint de TGI
client = InferenceClient(
    model="http://localhost:8080",  # URL al servidor TGI
)

# Generación de texto
response = client.text_generation(
    "Tell me a story",
    max_new_tokens=100,
    temperature=0.7,
    top_p=0.95,
    details=True,
    stop_sequences=[],
)
print(response.generated_text)

# Para formato de chat
response = client.chat_completion(
    messages=[
        {"role": "system", "content": "You are a helpful assistant."},
        {"role": "user", "content": "Tell me a story"},
    ],
    max_tokens=100,
    temperature=0.7,
    top_p=0.95,
)
print(response.choices[0].message.content)
```

Alternativamente, puedes usar el cliente de OpenAI:

```python
from openai import OpenAI
```

## Control avanzado de generación

### Selección de tokens y muestreo

El proceso de generación de texto implica seleccionar el siguiente token en cada paso. Este proceso de selección se puede controlar mediante varios parámetros:

1. **Logits en crudo**: Las probabilidades de salida iniciales para cada token
2. **Temperatura**: Controla la aleatoriedad en la selección (más alta = más creativa)
3. **Muestreo Top-p (Nucleus)**: Filtra los mejores tokens que componen el X% de la masa de probabilidad
4. **Filtrado Top-k**: Limita la selección a los k tokens más probables

Así es como se configuran estos parámetros:

<hfoptions id="inference-frameworks" >

<hfoption value="tgi" label="TGI">

```python
client.generate(

    temperature=0.8,  # Más alto para mayor creatividad
    top_p=0.95,  # Considera el 95% superior de la masa de probabilidad
    top_k=50,  # Considera los 50 tokens superiores
    max_new_tokens=100,  # Longitud máxima
    repetition_penalty=1.1,  # Reduce la repetición
)
```

## Gestión de memoria

Los frameworks implementan técnicas avanzadas de gestión de memoria para una inferencia eficiente.

<hfoptions id="inference-frameworks" >

<hfoption value="tgi" label="TGI">

TGI utiliza Flash Attention 2 y batching continuo:

```sh
# Despliegue con Docker y optimización de memoria
docker run --gpus all -p 8080:80 \
    --shm-size 1g \
    ghcr.io/huggingface/text-generation-inference:latest \
    --model-id HuggingFaceTB/SmolLM2-1.7B-Instruct \
    --max-batch-total-tokens 8192 \
    --max-input-length 4096
```

</hfoption>

<hfoption value="llama.cpp" label="llama.cpp">

llama.cpp utiliza cuantización y una disposición de memoria optimizada:

```sh
# Servidor con optimizaciones de memoria
./server \
    -m smollm2-1.7b-instruct.Q4_K_M.gguf \
    --host 0.0.0.0 \
    --port 8080 \
    -c 2048 \               # Tamaño del contexto
    --threads 4 \           # Hilos de CPU
    --n-gpu-layers 32 \     # Usa más capas en GPU para modelos más grandes
    --mlock \               # Bloquea la memoria para evitar el intercambio (swapping)
    --cont-batching         # Habilita el batching continuo
```

Para modelos demasiado grandes para tu GPU, puedes usar descarga a CPU (*CPU offloading*):

```sh
./server \
    -m smollm2-1.7b-instruct.Q4_K_M.gguf \
    --n-gpu-layers 20 \     # Mantiene las primeras 20 capas en GPU
    --threads 8             # Usa más hilos de CPU para las capas en CPU
```

</hfoption>

<hfoption value="vllm" label="vLLM">

vLLM utiliza PagedAttention para una gestión óptima de la memoria:

```python
from vllm.engine.arg_utils import AsyncEngineArgs

engine_args = AsyncEngineArgs(
    model="HuggingFaceTB/SmolLM2-1.7B-Instruct",
    gpu_memory_utilization=0.85,
    max_num_batched_tokens=8192,
    block_size=16,
)

llm = LLM(engine_args=engine_args)
```

</hfoption>

</hfoptions>
